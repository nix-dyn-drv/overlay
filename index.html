The headline number

nixgg's mechanism rebuilds only 2 of openssl's 2213 translation units on a one-line patch. dyn-drvs' mechanism builds clean on freetype, giflib, tree, figlet, and nnn, but freetype's patch-rebuild is 17x slower than a plain rebuild. Per-TU acceleration only pays off when each compile unit costs more than the ~80ms registration overhead it adds. A wider survey found every dyn-drvs failure traces back to either autotools' dependency-tracking idiom or cmake's generated build systems — every clean pass used a plain, hand-written Makefile.

Bugs found in dyn-drvs

Building and surveying more real nixpkgs packages against this repo surfaced nine distinct bugs in accelerate.mkAcceleratedStdenv, each written up for upstream:

  • discoverTree's dependency scan can't see a link step's own inputs when the link is driven through cc/c++ directly (cmake, libtool) — confirmed on zstd, pcre2, mpfr; not universal (tinycbor's own cc-driven links build fine).
  • autoreconfHook's dynamically-injected build phase gets silently dropped by a static phase list.
  • CMake's compiler-flag probes aren't recognized as passthrough-eligible, so a deferred stub falsely reports success.
  • The finalAttrs.finalPackage self-reference nixpkgs injects for ordinary packages is missing from the accelerated stdenv's own mkDerivation.
  • cmake builds can fail per-TU compiles with a source-not-found error — confirmed on xxHash, re2, and tinycbor's real (cmake-based) recipe.
  • A freshly-linked binary can lose its execute bit, breaking any Makefile that runs its own just-built binary as a self-test (libb64).
  • phases.split forces single-output but doesn't clear an inherited outputBin/outputMan literal override (libpng, libtasn1).
  • Secondary compiler side-outputs (automake's -MF depfiles) don't survive the sandbox boundary, breaking the classic autotools depcomp idiom (gperf).
